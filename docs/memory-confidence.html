Atlas Memory — Base vivante avec confiance évolutive

Approuvé platform/atlas-memory

Problème

Aujourd'hui, la base mémoire d'ATLAS stocke des expériences sans qualifier leur fiabilité.

Un agent scaffoldé avec un score juge de 2.0 (mauvais) et un agent avec un score de 5.0 (excellent) ont le même poids dans la base. Quand ATLAS cherche un template pour construire un nouvel agent, il peut tomber sur un mauvais exemple et croire que c'est du gold.

Conséquence concrète

Sur un nouveau projet similaire, ATLAS retrouve le scaffold raté de CategoryClassifier (score 1.0, prompt avec TODO) parce qu'il ressemble textuellement à la requête — et l'utilise comme point de départ. Le scaffold suivant repart d'une mauvaise base.

Principe fondamental

On ne supprime jamais. On qualifie.

Chaque entrée en base reste pour toujours — elle porte l'histoire. Ce qui change, c'est sa confiance : un score entre 0.0 et 1.0 qui dit à ATLAS « dans quelle mesure tu peux te fier à cette information ».

Analogie cerveau humain

« Je me souviens d'un agent de classification avec un prompt incomplet. Confiance : 0.2 — je sais que c'était raté. Je me souviens aussi d'un agent similaire qui marchait parfaitement. Confiance : 0.95 — validé par le juge. Je privilégie le second pour répondre à ta demande. »

Le KG, c'est ce que tu sais. Le RAG, c'est ce dont tu te souviens. Les deux s'affinent avec le temps.

Deux couches de mémoire

RAG — La mémoire épisodique

Stocke des expériences concrètes : du code généré, des évaluations de juge, des traces de pipeline. Technologie : Qdrant (base vectorielle locale, airGap-compatible).

Chaque expérience indexée contient désormais un champ confidence :

{
  "entry_type": "scaffold",
  "content": "Agent CategoryClassifier — classifie des tickets support...",
  "payload": {
    "agent_name": "CategoryClassifier",
    "run_id": "42b39d07-...",
    "judge_score": 5.0
  },
  "confidence": 0.95,   ← nouveau
  "timestamp": "2026-09-22T09:00:00Z"
}

KG — La mémoire sémantique

Stocke les relations entre concepts : quel agent produit quoi, qui enchaîne avec qui, quelles capacités sont maîtrisées. Chaque nœud agent porte maintenant son historique de scores :

{
  "name": "CategoryClassifier",
  "node_type": "agent",
  "capabilities": ["classification", "support-tickets"],
  "judge_score": 5.0,      ← nouveau : score le plus récent
  "confidence": 1.0,       ← nouveau : judge_score / 5.0
  "score_history": [         ← nouveau : trajectoire complète
    { "score": 1.0, "run_id": "abc...", "timestamp": "..." },
    { "score": 3.5, "run_id": "def...", "timestamp": "..." },
    { "score": 5.0, "run_id": "42b...", "timestamp": "..." }
  ],
  "coaching_history": [       ← existait déjà
    { "patch": "Remplacer TODO dans MAIN_PROMPT", "criterion": "output_format", "delta": 2.5 }
  ]
}

À chaque scaffold, la confiance de l'expérience précédente est réduite (mais pas supprimée). La nouvelle expérience est indexée avec une confiance proportionnelle à son score juge.

Impact sur la recherche RAG

Le score de pertinence combiné remplace le score cosine seul :

score_combiné = similarité_cosine × confidence

Avant — triés par similarité cosine uniquement

1. CategoryClassifier — run abc (scaffold #1) cosine 0.92 — judge 1.0
2. PriorityClassifier — run 42b (scaffold final) cosine 0.88 — judge 5.0
3. CategoryClassifier — run def (scaffold #2) cosine 0.85 — judge 3.5

← Le mauvais scaffold remonte en premier parce qu'il ressemble textuellement davantage à la requête.

Après — triés par score combiné

1. PriorityClassifier — run 42b 0.88 × 1.00 = 0.88
2. CategoryClassifier — run def 0.85 × 0.35 = 0.30
3. CategoryClassifier — run abc (invalidé) 0.92 × 0.00 = 0.00

Nouvelles opérations

update_confidence Affiner la fiabilité d'une expérience RAG existante 
# Quand un re-scaffold arrive avec un meilleur score,
# l'ancienne expérience perd de la confiance
memory.run(
    operation="update_confidence",
    point_id="uuid-de-l-ancienne-experience",
    confidence=0.3  # réduit car supplanté par mieux
)
invalidate Marquer comme dépassé sans supprimer — confidence → 0.0 
# Suppression d'un run de test par l'utilisateur
memory.run(
    operation="invalidate",
    point_id="uuid-du-scaffold",
    invalidated_by="user_delete"  # ou run_id_meilleur
)
# Résultat dans Qdrant :
# confidence = 0.0, invalidated_by = "user_delete"
# L'entrée reste — elle ne remonte plus dans les recherches
update_agent_score Mettre à jour le score et l'historique du nœud KG 
# Après chaque scaffold réussi ou installation
memory.run(
    operation="update_agent_score",
    name="CategoryClassifier",
    judge_score=5.0,
    run_id="42b39d07-..."
)
# Résultat dans graph.json :
# score_history += {score: 5.0, run_id: "42b...", timestamp: "..."}
# confidence = 5.0 / 5.0 = 1.0

Suppression d'un run — niveau 1

Endpoint : DELETE /api/runs/{run_id}

Action Ce qui se passe
Run store JSON Supprimé — ~/.atlas/runs/{run_id}.json
Fichiers scaffoldés disque Supprimés — répertoires output_path du run
Entrées RAG liées au run Invalidées — confidence = 0.0, conservées pour l'historique
Nœuds KG installés Non touchés — un agent installé reste dans le KG
Nœuds KG non installés confidence = 0.0 sur le nœud
Règle

Rien n'est jamais physiquement supprimé de Qdrant ni de graph.json. La suppression d'un run est une opération réversible au niveau de la base — seul le fichier JSON et les fichiers disque sont définitivement effacés.
